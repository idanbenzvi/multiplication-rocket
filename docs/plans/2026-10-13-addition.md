# Addition: a second mission for the same rocket

## Goal

The same game, every mode included, teaching **addition**. Each pilot chooses a mission when
they first start: **× Multiplication** or **+ Addition**. They can change it later in settings,
and each mission keeps its own progress.

Addition climbs through three stages. It moves up on mastery, not on time played:

| Stage | Range | Example | What's being learned |
| --- | --- | --- | --- |
| 1 | sums within 10 | 3 + 4 | counting on, doubles, pairs that make 10 |
| 2 | sums within 20 | 8 + 5 | crossing ten: 8 + 5 = 8 + 2 + 3 |
| 3 | numbers up to 100 | 37 + 45 | place value: tens and ones, then carrying |

This matches the usual school order (fluent within 10, then within 20, then two-digit within
100).

## The engine is already operation-agnostic (almost)

- Facts are `{a, b, key, product}` with key `"3x7"`. The picker, the dueScore weighting, the
  mastery gate on launching, the fuel and the answer log only ever look at the key and the
  answer. About 26 places across 9 files build or parse `"AxB"` or read `.product`.
- **Step 1** is an `Operation` module: `key(a, b)`, `answer(a, b)`, `symbol`, `pool(stage)`,
  `distractors`, `strategy`, `parse(key)`. Every caller goes through it, and multiplication
  behaves exactly as today. Keys become `"3+4"` for addition, so the two missions never mix.
- **Progress per mission:** a second progress key per pilot (`…:progress:v1:<id>:add`), so
  a child can fly both and the parent dashboard can show either.

## Stages, and moving between them

- Stages 1 and 2 have a small, fixed set of facts (an addition table, like the times table),
  so mastery per fact works as it does today.
- Stage 3 has about 5,000 pairs, so tracking each one is useless. Track **kinds** of problem
  instead: tens + tens, two-digit + one-digit (with or without carrying), two-digit + two-digit
  (with or without carrying). The picker weights the kinds, then builds a fresh problem of that
  kind.
- **Moving up:** like the Crew Flight navigator pool (`navigatorMax`), a stage opens once
  about 80% of the current one is mastered and nothing is struggling. Earlier facts stay in the
  mix (about 20%) so they aren't forgotten.

## Name

The app keeps one address. The logo and title follow the pilot's mission: **Multiplication
Rocket** (טיל הכפל) for ×, and the addition name for + (**SpaceSum**, or Addition Rocket,
טיל החיבור).

## Phases

1. **Core (done):** `game/mission.ts` (keys, symbols, answers), `game/addition.ts` (stages,
   kinds, advancement), the mission picker, distractors, hints, the addition map, the main drill,
   Meteor Shower, Wormhole, Monster Sun, Crew Flight (pilot, navigator and docking, mixed crews
   too), the parent dashboard's mission filter. Published to `/preview_addition/` (pushing to the
   `preview_addition` branch), next to the Monster Sun test at `/preview/`. Each preview keeps
   its own saved pilots.
2. **Bonus rounds rethought (done):** Constellation as a counting-on star chart (a ten-frame,
   two ten-frames, or a hundred chart, by the size of the sums), Fleet Battle as the missing part
   (cannons we have + ships needed = enemies), Stranded Fleet ([ ] + m), Stardust Run (equal
   jumps, then a pattern), Split Sky (each phone counts its group, then both add them). All six
   bonus rounds rotate for addition too; an addition host gets Split Sky only.
3. **Teaching:** the Addition Academy (done: three courses, one per stage, picked from a menu
   that marks the pilot's own stage; the Academy shell is shared with the multiplication one in
   `components/academy/parts.tsx`), then an addition two-phone game in place of Eclipse, badges.

## Testing

- Unit tests per operation: keys, answers, pools per stage, distractors (never the answer,
  never negative), strategies, stage advancement, and stage 3 kinds (carry or not).
- The existing multiplication tests must pass unchanged. They prove × still behaves the same.
- E2E: a new pilot picks + and plays through stage 1 into stage 2. A × pilot on the same device
  is unaffected.
